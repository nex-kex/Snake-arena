# Модель состояния сервера

Спецификация внутреннего состояния для реализации и командного ревью.
Соответствует `protocol.md` v1 и правилам `game-rules.md`.
Изменения согласуются всеми тремя участниками согласно `CONTRIBUTING.md`.
Документ описывает требуемое поведение; текущий `state.clj` ещё содержит заглушки.

## Граница общего состояния

Один `ref` содержит мир и метаданные всех открытых соединений. Только `state.clj`
создаёт этот `ref` и изменяет его внутри `dosync`. Подключённое соединение,
допущенный игрок и живая змейка — три разные сущности.

Реальные сокеты, WebSocket-каналы, функции отправки/закрытия находятся в отдельном
реестре транспорта по ID соединения. Они не включаются в мир и не передаются
чистым функциям правил. Метаданные соединения входят в общий `ref`, поскольку
кулдаун нужен даже после отказа в первом `join`.

## Начальное состояние

```clojure
{:config {:width 40
          :height 30
          :tick-ms 150
          :round-ms 180000
          :intermission-ms 5000
          :spawn-wait-ms 5000
          :join-cooldown-ms 5000
          :max-players 7
          :max-name-length 16
          :min-food 5
          :max-queued-turns 2}
 :tick 0
 :next-connection-id 1
 :next-player-id 1
 :next-entry-order 1
 :round {:number 0 :phase :waiting :deadline-ms nil}
 :connections {}
 :players {}
 :snakes {}
 :entries {}
 :spawn-claims {}
 :food #{}
 :last-result nil}
```

Начальное поле пустое. Еда создаётся при старте первого раунда.
Конфигурация неизменна в течение запуска; неуязвимости и `best-score` нет.
`tick` считает только выполненные игровые шаги и не сбрасывается между раундами.
Счётчики ID и порядка запросов увеличиваются транзакционно, не сбрасываются
между раундами и не переиспользуют выданные значения.

## Соединения

```clojure
{"c1" {:player-id "p1" :join-retry-at-ms nil}
 "c2" {:player-id nil :join-retry-at-ms 325000}}
```

- Ключ — внутренний ID соединения, например `c1`. Клиенту он не передаётся.
- `:player-id` — ID допущенного игрока либо `nil` до допуска.
- `:join-retry-at-ms` — монотонный срок кулдауна либо `nil`, если запрета нет.
- Число соединений не является числом игроков. Отказ `arena_full`, `invalid_name`
  или `invalid_kind` сохраняет соединение, но не создаёт игрока и не занимает место.
- Ссылка на игрока хранится только здесь. Обратная связь находится поиском
  по соединениям; отдельный дублирующий индекс не требуется.
- При отключении метаданные соединения удаляются. Переподключение получает новый
  ID соединения, а после допуска — новый ID игрока, без прежнего кулдауна.

## Игроки

```clojure
{"p1" {:name "Alice" :kind :human :score 4 :has-spawned? true}
 "p2" {:name "SnakeBot" :kind :bot :score 0 :has-spawned? false}}
```

- `:name` соответствует `^[A-Za-z]{1,16}$`, уникально среди `:players` с учётом
  регистра. Имя и `:kind` (`:human`/`:bot`) неизменны до отключения.
- `:score` — текущий счёт попытки. При смерти сохраняется; при успешном спавне
  начинается с 0 и затем увеличивается за еду под новым телом. Ожидание спавна
  само по себе не обнуляет счёт. Новый раунд обнуляет очки всех оставшихся игроков.
- `:has-spawned?` различает первое событие `spawn` и последующие `respawn` под
  тем же ID. Становится `true` при первом спавне и не сбрасывается между раундами.
- Мёртвые, ожидающие спавна и подтвердившие следующий раунд остаются в `:players`
  и занимают место. Максимум — 7, включая людей и ботов.
- Уникальность имён и лимит проверяются по этому словарю. Отдельный индекс имён
  для семи участников не требуется.

## Живые змейки и еда

```clojure
{"p1" {:body [[5 5] [4 5] [3 5]]
        :dir :right
        :queue [:up :left]
        :growth 0}}
```

- Ключ `:snakes` совпадает с ID игрока. Хранятся только живые змейки.
  Голова — первый элемент тела, шея — второй. Поля `:alive?` и `:grace` не нужны.
- `:dir` — `:up`, `:down`, `:left`, `:right`. `:queue` — вектор максимум из двух
  абсолютных направлений. Относительная команда преобразуется при приёме.
- `:growth` — целый неотрицательный запас роста. Каждая съеденная клетка даёт
  сразу +1 очко и +1 к запасу, за игровой тик расходуется максимум одна единица.
  При расходовании хвост не убирается. Еда от трупа начисляется после расчёта
  столкновений и даёт рост начиная со следующего тика; при спавне — с первого тика
  новой змейки. Рост в перерыве не выполняется.
- `:food` — множество уникальных `[x y]` в пределах поля. Генерация еды выбирает
  клетки без тел. Еда в области спавна не мешает появлению: под новым телом
  она сразу удаляется с начислением очков и запаса роста.
- При смерти в еду превращается тело после движения, только внутри поля.
  Погибшая змейка не получает очков за еду на тике смерти. Еда от трупа на клетках
  тела выжившей змейки сразу съедается ею, без пересчёта уже решённых столкновений.

## Запросы на участие и спавн

Единый словарь `:entries` хранит максимум один активный запрос на игрока.
Отдельное множество готовых и дублирующая очередь спавна не создаются.

```clojure
{"p2" {:stage :spawning
        :order 8
        :received-at-ms 320000
        :received-second 1800000000
        :deadline-ms 325000}}
```

| Поле | Значение |
|---|---|
| `:stage` | `:ready` — подтверждение во время перерыва; `:spawning` — активный поиск области в игре |
| `:order` | Уникальный возрастающий порядок принятого запроса |
| `:received-at-ms` | Монотонное время приёма, не меняется при ожидании |
| `:received-second` | Целая календарная секунда приёма: `floor(unix-ms / 1000)` |
| `:deadline-ms` | Для `:spawning` — срок ожидания; для `:ready` — `nil` |

В перерыве мёртвый или новый игрок получает запрос `:ready`. Живому запрос
не нужен: его готовность автоматическая. При начале игры `:ready` переводится
в `:spawning`, срок становится `now-ms + spawn-wait-ms`; исходные время и порядок
подачи сохраняются. Поиск места выполняется сразу, до следующего игрового тика.

При входе в текущую игру запрос сразу имеет `:stage :spawning` и такой же срок.
Если свободная область найдена, запрос потребляется в той же транзакции,
поэтому опубликованное состояние сразу имеет живую змейку без записи `:entries`.
Повторный запрос готового/ожидающего возвращает `already_pending`, не меняя
порядок, срок ожидания и счёт. При успешном спавне запись удаляется.

Запросы обслуживаются по `:received-at-ms`, затем `:order`. Область — минимум
5×5 без тел, наличие еды допустимо. Новое тело длины 3 размещается прямо;
его начальная ориентация выбирается алгоритмом размещения, движение — от шеи
к голове. Неуязвимости нет.

### Следы успешного спавна для конкуренции

Одного списка ожидающих недостаточно для правила v1: первый мог уже появиться
и удалить свой запрос, когда в ту же секунду пришёл второй. Для этого служит
непубликуемый словарь `:spawn-claims` по порядку успешного запроса:

```clojure
{7 {:player-id "p1" :received-second 1800000000}}
```

Запись добавляется при успешном спавне. Сначала для очередного запроса ищется
свободное место с учётом уже появившихся тел. Если места хватает — игрок появляется.
Если места не хватает из-за конкуренции с успешным запросом той же календарной
секунды, второй получает `spawn_conflict` и отключается; первый остаётся в игре.
Если такой конкуренции нет, запрос ожидает до своего срока.

Следы нужны только для незавершённой обработки запросов: сохраняются записи
текущей календарной секунды и секунд, на которые ещё ссылаются активные `:entries`.
Остальные удаляются; при выходе игрока его следы удаляются, при смене раунда
словарь очищается. Это служебная история, а не вторая очередь или рейтинг.

## Вычисляемые статусы протокола v1

Внутри игрока не хранятся дублирующие `:status`, `:alive?` и `:ready?`.

| Состояние | `players[].status` |
|---|---|
| Есть запись в `:snakes` | `alive` |
| Есть запись `:entries` со стадией `:spawning` | `spawning` |
| Есть запись `:entries` со стадией `:ready` | `ready` |
| Нет ни змейки, ни запроса | `dead` |

`players[].ready` равно `true` только при `:intermission`, если есть змейка
или запрос `:ready`. В остальных случаях `false`. `spawn_remaining_ms` —
остаток срока `:spawning`, иначе `null`. Таким образом, отсутствие змейки
само по себе не доказывает смерть.

## Фазы раунда и время

`:round` всегда содержит `:number`, `:phase`, `:deadline-ms`.

| Фаза | Срок | Действия |
|---|---|---|
| `:waiting` | `nil` | Нет игрового движения; принятый запрос запускает игру |
| `:playing` | Начало + 180000 мс | Движение, еда, команды поворота, спавн |
| `:intermission` | Окончание игры + 5000 мс | Рейтинг, вход/выход, подтверждение; без движения и роста |

`:number` увеличивается при каждом начале игры, включая новую игру после
прерывания. В перерыве/ожидании хранится последний номер, клиенту не передаётся.

Все сроки и `:received-at-ms` принадлежат одному источнику монотонных часов.
Календарное Unix-время используется только для `:received-second`, отметки
завершения рейтинга и `server_time_ms` в JSON. Нельзя сравнивать срок кулдауна
с Unix-временем или использовать календарные часы для длительности игры.

Остаток срока — `max(0, deadline-ms - now-ms)`. Достигнутый срок
(`now-ms >= deadline-ms`) обрабатывается раньше совпавшего действия.
Вход на границе конца перерыва не подтверждает участие задним числом,
тик на границе конца игры не исполняется, спавн на границе таймаута запрещён.
По достижении конца кулдауна, напротив, новый запрос уже разрешён.

Часы читаются вне `dosync`; монотонное и календарное время передаются аргументами
операции и не меняются при повторном выполнении STM-транзакции. Перед выполнением
действия сначала обрабатываются истёкшие фазы, затем оставшиеся актуальные
таймауты спавна. Конец раунда отменяет запросы старого раунда, они не переносятся.

## Рейтинг прошлого раунда

```clojure
{:completed-at-ms 1800000000000
 :ranking [{:player "p1" :name "Alice" :score 8 :rank 1}
           {:player "p2" :name "SnakeBot" :score 8 :rank 1}]
 :winners ["p1" "p2"]}
```

`:last-result` — `nil` до первого нормального завершения, затем независимая копия
ID, имён, очков, мест и победителей. Фиксируется по текущему `:players` до обнуления
очков. Ушедшие ранее не включаются, мёртвые оставшиеся включаются. Сортировка:
очки по убыванию, затем ID лексикографически. Место — 1 + число игроков со строго
большим счётом. Все с максимальным счётом побеждают, включая равенство нулей.

Выход игрока, освобождение имени и следующий раунд не изменяют сохранённую копию.
Следующее нормальное окончание заменяет её; выход последнего участника
и прерывание игры не создают нового результата. Перезапуск сервера очищает всё.
Постоянной таблицы рекордов, авторизации и `best-score` нет.

## Переходы состояния

Каждая операция ниже — одно атомарное изменение общего `ref`. События и ответы
перечислены как результаты операции, отправляемые после завершения транзакции.

| Переход | Изменения данных | Результат протокола |
|---|---|---|
| Открытие транспорта | Новый `cN`, `player-id nil`, без кулдауна; игрок/змейка не создаются | `hello`, персональный снимок |
| Отказ в первом входе | Только срок кулдауна соединения; имя и место не резервируются | `error`, персональный снимок |
| Ранний повтор | Данные запроса и срок кулдауна не меняются | `join_cooldown` с остатком |
| Первый допуск | Новый `pN`, связь в соединении, `score 0`, `has-spawned? false`; запрос по текущей фазе | `welcome`, `entry_result`, `join`, при немедленном появлении `spawn`, снимок |
| Повторный вход мёртвого | Новый запрос под прежним ID; счёт пока сохраняется; место/имя не резервируются повторно | `entry_result`, при немедленном появлении `respawn` либо первый `spawn`, снимок |
| Повторный вход живого/ожидающего | Только кулдаун от отказа; змейка, счёт и запрос не меняются | `already_alive` / `already_pending` |
| Успешный спавн | Удаление запроса, тело длины 3, пустая очередь, счёт с 0 плюс еда под телом, запас роста; `has-spawned? true`, след успешного запроса | `spawn` либо `respawn`, снимок |
| Поворот | Добавление допустимого направления в очередь без движения | Изменение видно в последующих тиках, отдельного ACK нет |
| Игровой тик | По одному повороту, движение, столкновения, еда/рост, смерть, пополнение еды; `tick + 1` | События смертей и полный снимок |
| Смерть | Удаление змейки, тело после движения становится едой в пределах поля; игрок и счёт остаются | `death`, снимок `dead` |
| Таймаут спавна | Удаление соединения, игрока, запроса и его следов; освобождение имени/места | `spawn_timeout`, закрытие; остальным `leave`, снимок |
| Проигрыш конкуренции | То же удаление для второго; данные первого сохраняются | `spawn_conflict`, закрытие; остальным `leave`, снимок |
| Подтверждение в перерыве | Запрос `:ready`, срок `nil`; счёт до начала игры сохраняется | `entry_result` со статусом `ready`, снимок |
| Выход / разрыв связи | Удаление соединения, игрока, змейки, запроса, следов и кулдауна; тело не становится едой | Остальным `leave`, снимок |

Таймаут и проигрыш конкуренции при первом допуске могут наступить до первого
появления змейки; имя и место всё равно освобождаются. После любого удаления
участника проверяется, остались ли игроки. Если во время игры их нет,
`:round.phase` становится `:waiting`, срок — `nil`; новый результат не создаётся.
Оставшиеся недопущенные соединения получают снимок ожидания.

### Нормальное окончание игры

1. Зафиксировать `:last-result` по текущим игрокам и счёту.
2. Установить фазу `:intermission`, срок перерыва. Тик на границе не выполняется.
3. Удалить запросы `:spawning`, каждому запросившему вернуть `spawn_cancelled`.
   Игроки остаются мёртвыми, счёт сохраняется для отображения; старый запрос
   не считается подтверждением нового участия.
4. Очистить следы спавна. Сохранить живые тела, направления и запас роста
   на время неподвижного перерыва. Повороты в перерыве отвергаются.
5. Отправить `round_result`, ошибки отмены спавна, затем снимок перерыва.
   Готовность живых вычисляется автоматически.

### Конец перерыва

1. Удалить мёртвых без `:ready` вместе с соединениями, освободить имена/места.
   Вернуть `not_ready`, закрыть транспорт; результат прошлого раунда не менять.
2. Если нет живых и запросов `:ready`, перейти в `:waiting`, срок `nil`.
   Не увеличивать номер, не запускать новый раунд. Рейтинг остаётся доступен.
3. Иначе выполнить запуск нового раунда одной транзакцией.

### Запуск игры из ожидания или после перерыва

1. Увеличить `:round.number`, установить `:playing` и срок на 180000 мс вперёд.
2. Обнулить очки всех оставшихся игроков, убрать старую еду и создать новую
   на свободных от живых тел клетках. Старый рейтинг сохранить.
3. Сохранить положение, длину и запас роста живых змеек; очистить очереди,
   вычислить направление от шеи к голове. `has-spawned?` не сбрасывать.
4. Запросы готовых перевести в `:spawning` со сроком 5000 мс от начала игры;
   время подачи и порядок сохранить. Первый запрос из ожидания обрабатывается
   так же, без обязательного прохождения через перерыв.
5. Обработать спавн по очереди. Успех удаляет запрос и создаёт змейку;
   при отсутствии места запрос остаётся, кроме проигрыша конкуренции.
6. Вернуть подтверждения новых запросов, события появлений и полный снимок.
   У автоматически перенесённых живых нет нового `spawn`/`welcome`/`entry_result`.

## Транзакции и порядок побочных эффектов

Чистые функции получают значение мира, действие и время и возвращают новый мир
с описанием исходящих сообщений/закрытий. Публичные операции `state.clj` применяют
результат через `dosync` к одному `ref`. Отправка JSON, закрытие сокетов, чтение
часов и непредсказуемая генерация случайных значений внутри транзакции запрещены.
Выбор случайного спавна/еды должен воспроизводиться при STM-повторе: например,
использовать переданный источник выбора или состояние детерминированного генератора.

Изменение мира и фиксация описания его результата выполняются атомарно.
После commit публикация следует тому же порядку, что изменения мира: единый
диспетчер операций и отправок либо упорядоченная очередь результатов.
Нельзя отправлять независимо из конкурирующих callback: старый снимок может
обогнать новый. Сетевые отправки не должны задерживать саму STM-транзакцию.

При принудительном отключении операция атомарно удаляет логические данные,
а её результат содержит ошибку и команду закрытия по ID соединения. Транспорт
сохраняет дескриптор до попытки отправить терминальную ошибку, затем закрывает его.
Логическое удаление не отменяет отправку ошибки по ещё открывавшемуся транспорту.

## Проекция в протокол v1

Чистая `broadcast/world->state-update` формирует общую часть из одного значения
мира и фиксированного времени. Для соединения добавляется `self`.

| JSON v1 | Источник |
|---|---|
| `tick` | `:tick` |
| `round.phase` | Строка из `[:round :phase]` |
| `round.remaining_ms` | Остаток `[:round :deadline-ms]`; `null` в ожидании |
| `players` | Массив из `:players`, статус/готовность по таблице выше |
| `snakes` | Массив из `:snakes`, ID из ключа, имя из `:players`, `alive: true` |
| `food` | Массив из множества `:food` |
| `scores` | Объект ID → `:score` из `:players` |
| `self.player` | `:player-id` соединения либо `null` |
| `self.join_retry_after_ms` | Остаток `:join-retry-at-ms` соединения либо 0 |
| `last_result` | Копия `:last-result`, ключи в формате протокола, либо `null` |
| `server_time_ms` | Переданное календарное время формирования снимка |

Игроки и змейки сортируются по ID лексикографически, еда — по `(x,y)`.
Направления и фазы превращаются из keywords в строки, `nil` — в JSON `null`.
Внутренние сроки, номер раунда, соединения, очередь поворотов, запас роста,
запросы и следы спавна не публикуются. В протоколе публикуются только остатки
сроков и вычисленные статусы. Новый снимок заменяет предыдущий целиком.
Текущие TS-типы и Prolog-парсер должны быть дополнены для всего контракта v1.

## Инварианты и критерии проверки

- У каждого `:player-id` из соединений есть игрок. Каждый игрок связан ровно
  с одним соединением; два соединения не могут управлять одним игроком.
- Не более 7 игроков; имена уникальны с учётом регистра и соответствуют шаблону.
  Проверки и резервирование выполняются в одной транзакции.
- Ключи `:snakes` и `:entries` — подмножества ключей `:players`, они не пересекаются.
- `:ready` встречается только в перерыве, `:spawning` — только в игре.
  Готовый запрос не имеет срока спавна, ожидающий имеет срок.
- Живая змейка принадлежит игроку с `has-spawned? true`. Длина не меньше 3,
  направление допустимо, очередь не длиннее 2, запас роста целый неотрицательный.
- Тела не пересекаются в опубликованном состоянии; координаты тел/еды внутри поля.
  Еда от трупа или под новым телом потребляется до публикации снимка.
- `:waiting` имеет срок `nil`, игра и перерыв — монотонный срок; номер и `tick`
  неотрицательны. Ни обновление таймера, ни перерыв не увеличивают `tick`.
- Мёртвый игрок может существовать в игре/перерыве, но неподтвердивший не остаётся
  после конца перерыва. Таймаут спавна удаляет участника, освобождая имя/место.
- Счёт, времена и готовность в JSON выводятся из того же снимка, что тела и еда.
- Сохранённый рейтинг не зависит от дальнейших изменений `:players`.
- После отключения удалены все связанные данные; следующий транспорт не наследует
  ID, счёт, тело, запросы или кулдаун. ID игроков и порядок запросов не переиспользуются.
- При двух конкурентных `join` на последнее место допускается только один;
  при двух запросах одного имени допускается только один. Это проверки STM,
  а не предварительные проверки вне транзакции.
