# Протокол Snake Arena v1

Статус: спецификация для реализации и командного ревью. Изменения этого файла
и `state-model.md` согласуются всеми тремя участниками согласно `CONTRIBUTING.md`.
Существующий код ещё не реализует весь контракт v1.
Игровые правила — в `game-rules.md`, внутреннее состояние — в `state-model.md`.

## Транспорт и общие соглашения

- Браузер: WebSocket, порт 8080, путь `/`, одно текстовое JSON-сообщение на кадр.
- Бот: TCP, порт 9090, UTF-8, одно JSON-сообщение на строку с завершающим `\n`.
  Разделение TCP-пакетов не является разделением сообщений. Пустая строка — `bad_json`.
- Сообщение — JSON-объект с обязательным строковым `type`. Числовые строки
  не заменяют числа; обязательные поля нельзя опускать или заменять `null`.
  `null` разрешён только там, где явно указан ниже.
- Координаты — пары целых `[x,y]`, начало сверху слева. Направления:
  `up`, `down`, `left`, `right`. ID — непрозрачная строка, уникальная с момента
  запуска сервера; имя не является ID. ID после отключения не переиспользуется.
- Длительности — целые неотрицательные миллисекунды. `server_time_ms` — Unix time
  сервера в миллисекундах на момент формирования сообщения. Для таймеров клиент
  использует переданное оставшееся время и локально уменьшает его; часы клиента
  не определяют исход игры. Сервер измеряет интервалы монотонными часами.
- В одном соединении сообщения обрабатываются и отправляются последовательно.
  Между соединениями сервер задаёт единый порядок принятых действий.
- Неизвестные дополнительные поля игнорируются. Неизвестный `type` от клиента
  вызывает `unknown_type`; клиент/бот игнорирует неизвестный серверный `type`.
- `protocol_version: 1` передаётся в `hello` и `welcome`. При неподдерживаемой
  версии клиент показывает ошибку совместимости и закрывает соединение.
- Авторизации, восстановления сессии и постоянной таблицы рекордов нет.
  Номер раунда существует только внутри сервера и не передаётся ни человеку, ни боту.

## Подключение и идентичность

Соединение само по себе не занимает место среди семи участников. После открытия
сервер отправляет `hello`, затем полный персонализированный `state_update`.
До `join` клиент уже видит поле, фазу, таймер и последний рейтинг, но не управляет
змейкой. В отказе соединение обычно остаётся открытым для новой попытки.

### `hello` — сервер → соединение

```json
{"type":"hello","protocol_version":1,"config":{"width":40,"height":30,"tick_ms":150,"round_ms":180000,"intermission_ms":5000,"spawn_wait_ms":5000,"join_cooldown_ms":5000,"max_players":7,"max_name_length":16,"min_food":5,"max_queued_turns":2}}
```

Все поля `config` обязательны. Параметра неуязвимости нет.

### `join` — клиент → сервер

```json
{"type":"join","name":"Alice","kind":"human"}
```

- `name`: `^[A-Za-z]{1,16}$`, уникально среди допущенных участников с учётом
  регистра. `Alice` и `alice` различны. `kind`: `human` или `bot`.
- Проверка имени, лимита и добавление участника выполняются атомарно.
  Мёртвые, готовые к следующему раунду и ожидающие спавна занимают места.
- Первый принятый `join` создаёт участника и запускает раунд из `waiting`.
  При `playing` участник входит в текущий раунд, при `intermission` становится
  готовым к следующему. Вход не продлевает текущий таймер.
- После допуска имя и `kind` неизменны до отключения. Повторный `join`
  того же соединения с теми же значениями означает повторный вход/подтверждение
  участия. Другие значения дают `identity_mismatch`, без изменения идентичности.
- При собственном повторном входе имя и место повторно не резервируются:
  проверка уникальности не считает самого участника конфликтом, заполненная
  арена не мешает повторному входу уже допущенного мёртвого участника.
- Живому участнику повторный вход запрещён (`already_alive`). Ожидающему
  спавна или уже готовому участнику повторный запрос даёт `already_pending`.
  Запрос не изменяет счёт, очередь спавна и срок ожидания.

### `welcome` — сервер → впервые допущенный участник

```json
{"type":"welcome","protocol_version":1,"you":"p1","config":{"width":40,"height":30,"tick_ms":150,"round_ms":180000,"intermission_ms":5000,"spawn_wait_ms":5000,"join_cooldown_ms":5000,"max_players":7,"max_name_length":16,"min_food":5,"max_queued_turns":2}}
```

Приходит ровно один раз после первого принятого `join`, даже если спавн ещё
ожидается или идёт перерыв. Это подтверждение допуска, а не появления змейки.
После него сервер отправляет `entry_result`, события и полный снимок.
Повторный вход под тем же соединением не вызывает нового `welcome`.

### `entry_result` — сервер → подавший запрос на вход

```json
{"type":"entry_result","player":"p1","status":"spawning","spawn_remaining_ms":5000}
```

Поля обязательны: `player` — ID; `status` — `alive`, `spawning` или `ready`;
`spawn_remaining_ms` — число только при `spawning`, иначе `null`.
Сообщение подтверждает каждый принятый запрос (первый `join`, повторный `join`
или `respawn`). При немедленном спавне `status: "alive"`; при приёме в перерыве
`status: "ready"`. Уже живые, готовые и ожидающие получают ошибку, а не подтверждение.
Последующий переход из ожидания в живое состояние виден в `event` и снимке.

## Команды клиента

### `command`

```json
{"type":"command","text":"go up"}
```

`text` — обязательная строка. Перед разбором удаляются внешние пробелы,
последовательности внутренних пробельных символов заменяются одним пробелом,
регистр команды игнорируется. Это не меняет регистр имени в `join`.
Принимаются следующие точные фразы после нормализации:

| Фразы | Действие |
|---|---|
| `go up`, `иди вверх` | Абсолютный поворот вверх |
| `go down`, `иди вниз` | Вниз |
| `go left`, `иди влево` | Влево |
| `go right`, `иди вправо` | Вправо |
| `turn left`, `поверни налево` | Относительный поворот налево |
| `turn right`, `поверни направо` | Относительный поворот направо |
| `respawn`, `возродиться` | Повторный вход/подтверждение участия |
| `score`, `scores`, `покажи счёт`, `покажи счет` | Ответ `scores` |
| `players`, `кто играет` | Ответ `players` |
| `help`, `помощь` | Ответ `help` |

- `respawn` требует ранее принятого `join` и использует сохранённые имя и `kind`.
  В игре запрашивает спавн, в перерыве — готовность, в ожидании запускает раунд.
  По проверкам и результатам эквивалентен повторному `join`.
- Повороты допустимы только для живой змейки в `playing`. В перерыве/ожидании
  возвращается `not_playing`, для мёртвого/ожидающего — `not_alive`.
- При допущенном повороте отдельного подтверждения нет. Очередь до 2,
  один поворот за тик. Повтор направления, разворот на 180° и переполнение
  молча игнорируются, как в `game-rules.md`.
- `players`, `scores`, `help` доступны и до допуска. Остальные команды без
  принятого `join` дают `not_joined`. Неизвестная фраза — `unknown_command`.
- Бот может добавить необязательное строковое поле `reason` в `command`
  для объяснения решения. Сервер не использует его для игровой логики и не рассылает.
  Это диагностическое поле, оно не обязательно для корректной команды.

### `leave`

```json
{"type":"leave"}
```

Эквивалент закрытию соединения. Сервер удаляет участника, змейку без образования
еды, запросы и кулдаун, освобождает имя/место, отправляет остальным `leave`
и снимок, затем закрывает соединение. Кнопка «Выйти из раунда» использует `leave`
или закрывает транспорт. Отдельного подтверждения выхода нет.

## Полный снимок мира

### `state_update` — сервер → все открытые соединения

```json
{
  "type":"state_update",
  "server_time_ms":1800000000000,
  "tick":12,
  "round":{"phase":"playing","remaining_ms":168000},
  "players":[
    {"id":"p1","name":"Alice","kind":"human","status":"alive","ready":false,"spawn_remaining_ms":null},
    {"id":"p2","name":"SnakeBot","kind":"bot","status":"spawning","ready":false,"spawn_remaining_ms":2400}
  ],
  "snakes":[{"id":"p1","name":"Alice","body":[[5,5],[4,5],[3,5]],"dir":"right","alive":true}],
  "food":[[10,10],[20,20]],
  "scores":{"p1":2,"p2":0},
  "self":{"player":"p1","join_retry_after_ms":0},
  "last_result":null
}
```

Все верхнеуровневые поля обязательны. Пример показывает формат массива еды,
а не полный мир с минимальным количеством еды из конфига.

| Поле | Контракт |
|---|---|
| `tick` | Целое неотрицательное число игровых шагов с запуска сервера. Не сбрасывается между раундами. Вне игры не увеличивается. Это не номер раунда. |
| `round.phase` | `waiting`, `playing`, `intermission` |
| `round.remaining_ms` | Остаток текущей игры/перерыва, в `waiting` — `null` |
| `players` | Все допущенные участники; отклонённые соединения сюда не входят |
| `snakes` | Только живые змейки, голова — первая клетка `body` |
| `food` | Уникальные пары координат в пределах поля |
| `scores` | Текущие очки каждого ID из `players`, включая мёртвых |
| `self.player` | ID получателя после допуска, до допуска — `null` |
| `self.join_retry_after_ms` | Остаток кулдауна получателя; 0, если запрета нет |
| `last_result` | Последний зафиксированный рейтинг либо `null`, структура ниже |

`tick`, очки, места в рейтинге, размеры поля и интервалы — целые числа;
очки и `tick` неотрицательны, размеры и места положительны. `body` — массив
не менее трёх пар целых координат в пределах поля; в опубликованном снимке
тела не пересекаются. Все ID змеек есть в `players`, `scores` содержит ровно
тот же набор ID, что `players`. `name` в змейке совпадает с именем её игрока.
`ready` и `alive` — JSON boolean, не строки.

Объект игрока всегда содержит все показанные поля:

- `status`: `alive` (есть змейка), `dead` (нет змейки и запроса), `spawning`
  (активный поиск области), `ready` (подтверждён следующий раунд в перерыве).
- `ready`: в перерыве `true` для живых автоматически и для подтвердивших вход;
  вне перерыва `false`. Живой в перерыве имеет `status: "alive"`, а не `ready`.
- `spawn_remaining_ms`: оставшееся ожидание только при `spawning`, иначе `null`.
- Змейка содержит `id`, `name`, `body`, `dir`, `alive`. `alive` всегда `true`,
  сохранено для совместимости с текущими TS-типами и DCG-парсером бота.
  Смерть означает отсутствие змейки в новом снимке; `alive: false` не передаётся.

Внутренние `queue`, `growth`, таймерные отметки и номер раунда не публикуются.
Словари змей преобразуются в массивы, множества еды — в массивы координат,
Clojure keywords — в строки. `players`/`snakes` упорядочены по ID лексикографически,
еда — по `(x,y)`. Порядок ключей JSON-объекта не имеет значения.

Каждый снимок полностью заменяет предыдущие `players`, `snakes`, `food`, `scores`
и сведения о фазе. Массивы не дополняются старыми записями. `self` персонализирован,
общие поля строятся из одного согласованного значения мира после транзакции.
Сеть и JSON-кодирование выполняются вне `dosync`.

Снимки отправляются сразу после `hello`, после каждого игрового тика, изменения
состава/готовности, спавна/смерти, смены фазы и изменения кулдауна получателя.
В `waiting`/`intermission` и при активном ожидании спавна сервер дополнительно
обновляет снимок не реже раза в `tick_ms`, чтобы синхронизировать таймеры;
игровой `tick` от этого не увеличивается. При отсутствии соединений рассылки нет.
Снимок на одном соединении отправляется в порядке серверных изменений.

## Рейтинг и информационные ответы

### `round_result`

```json
{"type":"round_result","result":{"completed_at_ms":1800000000000,"ranking":[{"player":"p1","name":"Alice","score":8,"rank":1},{"player":"p2","name":"SnakeBot","score":8,"rank":1},{"player":"p3","name":"Bob","score":3,"rank":3}],"winners":["p1","p2"]}}
```

Сервер фиксирует результат до сброса очков, отправляет всем соединениям при
нормальном окончании раунда, затем отправляет снимок с фазой `intermission`.
Внутри `last_result` находится ровно объект `result` (без `type`).
Рейтинг включает всех участников, находящихся в `players` на границе окончания,
в том числе мёртвых. Ушедшие до границы не включаются. Все с максимальным счётом
побеждают, в том числе при нулевых очках. Пустой рейтинг имеет `winners: []`.

Сортировка: очки по убыванию, при равенстве ID лексикографически.
Место — 1 + число участников со строго большим счётом: 1, 1, 3.
Равенство ID для сортировки не влияет на право разделить победу.
Результат хранит копии имён и очков; последующий выход игрока его не меняет.
При прерывании из-за выхода последнего участника новый результат не создаётся.
Последний результат доступен до следующего нормального окончания или перезапуска
сервера; это временный снимок, а не постоянная таблица рекордов.

### `players`

```json
{"type":"players","players":[{"id":"p1","name":"Alice","kind":"human","status":"alive","ready":false,"spawn_remaining_ms":null}]}
```

Ответ только запросившему; элементы имеют тот же контракт, что в снимке.

### `scores`

```json
{"type":"scores","scores":{"p1":2},"ranking":[{"player":"p1","name":"Alice","score":2,"rank":1}]}
```

Ответ только запросившему. Это текущий счёт, не итог прошлого раунда.
`ranking` сортируется и ранжируется так же, как `round_result`.

### `help`

```json
{"type":"help","commands":[{"command":"go up|down|left|right","description":"Абсолютное направление"},{"command":"turn left|right","description":"Относительный поворот"},{"command":"respawn","description":"Повторный вход в раунд"},{"command":"scores","description":"Текущий счёт"},{"command":"players","description":"Список участников"},{"command":"help","description":"Справка"}]}
```

Ответ только запросившему, массив содержит все шесть показанных записей.
Строки описаний информационные; программа использует `command`, а не текст описания.
Русские алиасы принимаются согласно таблице команд выше.

## События

### `event`

```json
{"type":"event","kind":"death","player":"p1","reason":"wall"}
```

Все четыре поля обязательны. `kind`: `join`, `spawn`, `respawn`, `death`, `leave`.
`reason` для `death`: `wall`, `head_to_head`, `head_swap`, `self_body`, `other_body`.
При нескольких причинах выбирается первая из этого списка. Для остальных событий
`reason: null`. События отправляются всем соединениям для лога, после изменения
мира и до соответствующего снимка; клиент не должен восстанавливать мир только
по событиям. Несколько событий одного изменения сортируются по ID, для одного
ID: `join` перед `spawn`/`respawn`, `death` перед `leave`.

`join` — только первый допуск; `spawn` — первое появление змейки под этим ID,
`respawn` — последующие появления, `leave` — любое удаление допущенного участника.
Автоматический перенос живой змейки между раундами не вызывает нового `spawn`.
Ошибка отклонённого соединения, не ставшего участником, не вызывает `leave`.

## Ошибки и кулдаун

### `error`

```json
{"type":"error","code":"arena_full","message":"Арена заполнена","retry_after_ms":5000,"disconnect":false}
```

Все поля обязательны. `message` предназначен человеку; логика использует `code`.
`retry_after_ms` — остаток кулдауна, а не указание ботам безусловно повторять запрос.
`disconnect: true` означает, что сервер после отправки ошибки закрывает соединение.
Обычный отказ во входе сохраняет соединение и запускает кулдаун 5000 мс от отказа.
Ранняя попытка возвращает `join_cooldown` с остатком, не продлевая срок.
Кулдаун относится только к входу (`join` и `respawn`), не к `help` или поворотам.
Истечение кулдауна само по себе не повторяет запрос на вход.

| Код | Условие | Новый кулдаун | Закрытие |
|---|---|---|---|
| `bad_json` | Строка/кадр не является корректным JSON | Нет | Нет |
| `bad_message` | JSON не объект, нет строкового `type` или неверная форма команды | Нет | Нет |
| `unknown_type` | Неизвестный строковый `type` | Нет | Нет |
| `invalid_name` | Имя не соответствует шаблону или поле отсутствует/не строка | 5000 мс | Нет |
| `name_taken` | Такое имя уже занято другим участником | 5000 мс | Нет |
| `invalid_kind` | Поле отсутствует или не `human`/`bot` | 5000 мс | Нет |
| `arena_full` | Семь мест заняты, запрашивается новый допуск | 5000 мс | Нет |
| `identity_mismatch` | Повторный `join` меняет имя или `kind` | 5000 мс | Нет |
| `already_alive` | Повторный вход живого | 5000 мс | Нет |
| `already_pending` | Вход при готовности или ожидании спавна | 5000 мс | Нет |
| `join_cooldown` | Новый запрос до конца кулдауна | Нет, остаток прежнего | Нет |
| `not_joined` | Игровая команда/`respawn` до допуска | Для `respawn` 5000 мс, иначе нет | Нет |
| `unknown_command` | Неизвестная текстовая фраза | Нет | Нет |
| `not_playing` | Поворот во время ожидания или перерыва | Нет | Нет |
| `not_alive` | Поворот мёртвого/готового/ожидающего спавна | Нет | Нет |
| `spawn_timeout` | Истекло ожидание спавна | Нет | Да |
| `spawn_conflict` | Конкуренция за место в одну секунду, второй проиграл | Нет | Да |
| `spawn_cancelled` | Раунд закончился до спавна; нужен новый вход | Нет | Нет |
| `not_ready` | Мёртвый не подтвердил участие к концу перерыва | Нет | Да |
| `phase_expired` | Действие совпало с истечением фазы/срока и не выполнено | Нет | Нет |

`not_dead` из раннего черновика не используется: повторный вход живого всегда
даёт `already_alive`. При ошибке без нового кулдауна `retry_after_ms` всё равно
отражает остаток уже существующего кулдауна; при закрытии — 0.

Порядок проверки `join`: сначала истёкшие таймеры, затем кулдаун, имя, `kind`,
неизменность идентичности (для допущенного), собственный статус, уникальность имени,
лимит. Успешный повторный вход использует уже занятое собственное место.
Порядок `command`: форма (включая тип необязательного `reason`), разбор фразы, для повторного входа кулдаун/допуск/статус;
для поворота допуск, фаза, наличие живой змейки. `reason` при наличии должен быть
строкой; иначе `bad_message`. Синтаксическая ошибка JSON не запускает кулдаун.

При отключении по ошибке сервер сначала пытается отправить `error`, затем
удаляет участника и закрывает транспорт. Для WebSocket используется код 1000
для обычного выхода и 1008 для принудительного отключения; для TCP — EOF.
Если соединение уже оборвалось, доставка последней ошибки не гарантируется.
Новый транспорт не наследует ID, запросы, счёт, тело и кулдаун.

## Последовательности сообщений

Стрелки ниже задают порядок на одном соединении; сообщения другим получателям
могут находиться между ними. Снимки после одного изменения допускается объединять,
но подтверждение и ошибки нельзя пропускать.

### Первый вход и вход посреди игры

1. Сервер → `hello`, затем снимок с `self.player: null` и текущей фазой.
2. Клиент → `join`.
3. Сервер → `welcome`, `entry_result` (`alive` или `spawning`), события `join`
   и, если появилась змейка, `spawn`, затем снимок с собственным ID.
4. Если спавн отложен: дальнейшие снимки содержат `spawning` и остаток ожидания;
   при появлении — `spawn`/`respawn`, затем снимок `alive`.

Посреди игры новый участник получает актуальные поле и оставшееся время, без
перезапуска раунда. Счёт попытки начинается с 0, затем начисляется еда под новым телом.

### Снимок до входа при ожидании участников

```json
{"type":"state_update","server_time_ms":1800000000000,"tick":0,"round":{"phase":"waiting","remaining_ms":null},"players":[],"snakes":[],"food":[],"scores":{},"self":{"player":null,"join_retry_after_ms":0},"last_result":null}
```

Пустая еда в этом примере относится к ещё не запущенному первому раунду.
Если после прошлого раунда осталась еда, снимок содержит её актуальное состояние;
при старте следующего раунда еда генерируется заново.

### Вход в перерыве

1. После открытия: `hello`, снимок `intermission` с оставшимся временем и `last_result`.
2. После первого `join`: `welcome`, `entry_result` со статусом `ready`, `join`, снимок.
3. По концу перерыва: новый снимок `playing`, для нового участника `spawn`
   перед снимком либо состояние `spawning` со сроком 5000 мс.
4. Живые сохраняют тело, получают нулевой счёт и очищенную очередь;
   направление вычисляется от шеи к голове. Мёртвые без подтверждения получают
   `not_ready` и отключаются. Их выход не изменяет уже сохранённый рейтинг.

Пример ответа на вход в перерыве:

```json
{"type":"entry_result","player":"p4","status":"ready","spawn_remaining_ms":null}
```

Пример немедленного появления в игре:

```json
{"type":"entry_result","player":"p4","status":"alive","spawn_remaining_ms":null}
```

### Смерть и повторный вход

1. Сервер → `death`, снимок со статусом `dead`, без змейки, с сохранённым счётом.
2. Клиент → `command` с `text: "respawn"` либо повторный `join` с прежним именем/`kind`.
3. Сервер → `entry_result`, при спавне `respawn`, затем снимок.
   ID сохраняется; счёт обнуляется при успешном спавне, а не при начале ожидания.
4. При конце раунда раньше спавна → `round_result`, `spawn_cancelled`, снимок
   `intermission` со статусом `dead`. Старый запрос не становится готовностью.
   Нужно подтвердить участие до конца перерыва.

### Отказ, таймаут и границы времени

Пример ранней повторной попытки (остаток прежнего кулдауна):

```json
{"type":"error","code":"join_cooldown","message":"Повторите вход позже","retry_after_ms":3200,"disconnect":false}
```

Пример принудительного отключения после ожидания спавна:

```json
{"type":"error","code":"spawn_timeout","message":"Свободное место не найдено за 5 секунд","retry_after_ms":0,"disconnect":true}
```

- Обычный отказ: `error` с `disconnect: false` и кулдауном, затем персональный снимок.
  Ранний повтор даёт `join_cooldown`; новая попытка после срока — явно от клиента.
- Таймаут спавна: `error` `spawn_timeout`, удаление участника, закрытие;
  остальным `leave` и снимок. Повторный транспорт — новый игрок без кулдауна.
- Конкуренция: первый занимает доступное место, второй при конкуренции в ту же
  календарную секунду получает `spawn_conflict` и отключается. Если места хватает
  обоим, оба входят. Первая змейка не удаляется и не ждёт конца секунды.
- При достижении срока таймер обрабатывается раньше действий: тик на границе
  конца раунда не выполняется, спавн на границе таймаута не выполняется,
  подтверждение на границе конца перерыва не учитывается для его запуска.
  Адресуемое отклонённое действие получает `phase_expired`, если соединение
  ещё открыто и не было отправлено более конкретное `spawn_timeout`/`not_ready`.
- Таймер кулдауна — исключение: при остатке 0 новый вход уже разрешён.
- При уходе последнего участника игра прерывается без нового `round_result`.
  Неприсоединившиеся открытые соединения получают снимок `waiting`.

## Проверки контракта перед реализацией

- Браузер и бот видят одинаковые общие поля снимка; отличается только `self`.
- До допуска/после отказа нет занятого места и имени; после допуска их не больше 7.
- Повторный вход не требует нового места/ID и не конфликтует с собственным именем.
- Погибшие отсутствуют в `snakes`, но присутствуют в `players`/`scores` до выхода.
- Новый клиент в игре/перерыве получает весь контекст без истории старых сообщений.
- Повторные запросы не продлевают кулдаун и ожидание спавна.
- Рейтинг фиксируется до сброса, сохраняет имена ушедших и содержит всех победителей.
- Истечение таймера приоритетнее тика/спавна/подтверждения, перерыв не двигает змей.

## Совместимость с текущим кодом

`client/src/types.ts` пока описывает лишь часть снимка. `bot/src/parser.pl`
разбирает `welcome`, базовые `state_update`, `event`, `error`, но не все сообщения v1.
`bot/bot.pl` пока выбирает действие на каждом снимке, не проверяя фазу и свой статус.
Перед интеграцией нужно добавить обработку `hello`, `entry_result`, таймеров,
готовности и рейтинга, принять `reason: null` у событий без причины,
а также не отправлять повороты/`respawn` на каждый снимок
в перерыве или при активном запросе спавна. Сохранение `alive: true` и прежних
базовых полей не делает существующий бот полностью совместимым с v1.
